# AQUILIA — MIGRATION AUDIT & ENGINEERING FINDINGS

**Scope:** findings discovered *while* migrating the AniWave backend from
Node.js/NestJS into a native Aquilia application (`backend/`), during actual
implementation, integration, testing, debugging, and verification (2026-09-14).
This is not an independent framework review: nothing below is speculative, and
every item was encountered through the migration work itself.

**Aquilia version:** 1.4.0 ("Grand Armida"), Python 3.13, source read from the
installed package and the reference checkout at `tmp/Aquilia/` (identical
version). **AniWave result context:** migration completed and verified — 46
routes, 6 modules, 108/108 tests, `aq validate` 9/9, live boot with real
Postgres/Redis/AniList. The app works *because* the defects below were worked
around; they are recorded anyway.

**Provenance key:** *runtime* = observed while the app ran; *source* = read
from Aquilia source and matched observed behavior; *test* = reproduced under
the AniWave test suite; *CLI* = observed via `aq` commands during the build.

### F-01 — `ArrayField` cannot be serialized into migrations (documented field type is unusable in the migration system)

- **Severity:** Critical
- **Status:** confirmed + workaround (field abandoned)
- **Affected Aquilia component:** ORM — `Field.deconstruct()` / `ArrayField` / migration codegen
- **Location:** `aquilia/models/fields_module.py` — `Field.deconstruct()` (~line 463) serializes only `type/null/unique/primary_key/db_index` (+ conditional `db_column`, non-callable `default`); `ArrayField` (~line 3094) does **not** override `deconstruct()` to include `base_field`. `aquilia/models/migration/schema.py` `ColumnState.from_field()` builds `field_kwargs` from `deconstruct()`.
- **How discovered:** `User.preferred_genres` was declared `ArrayField(TextField())` (matching the Node `text[]` column). `aq db makemigrations` generated a migration containing `ColumnState.of("preferred_genres", fields.ArrayField())` — the constructor argument was silently dropped.
- **Actual behavior:** `aq db migrate` failed: `ArrayField.__init__() missing 1 required positional argument: 'base_field'`. The schema snapshot (`schema_snapshot.json`) is lossy in the same way (`{"field_class": "ArrayField"}` with no params).
- **Expected behavior:** a documented, exported field type round-trips through the migration system.
- **Impact on AniWave:** forced a deliberate schema deviation — `preferred_genres` became `JSONB` via `JSONField`, requiring an in-place conversion of the existing dev database (`array_to_json(...)::jsonb`) with data preservation.
- **Workaround used:** `JSONField(null=False, default=list)`; dev DB converted via `ALTER TABLE ... USING array_to_json(preferred_genres)::jsonb` (also had to `DROP DEFAULT` first — the drizzle `'{}'::text[]` default blocked the cast).
- **Recommended fix:** override `deconstruct()` on `ArrayField` (and audit every field with constructor args that affect DDL) to serialize `base_field` (and `size`); add a round-trip test: model → snapshot → rebuild → identical DDL.

### F-02 — Generated FK migrations render INTEGER columns for UUID-keyed targets; migration apply fails

- **Severity:** Critical
- **Status:** confirmed + workaround (hand-edited migration file)
- **Affected Aquilia component:** migrations — codegen + `ForeignKey.sql_type()` + `cmd_migrate`
- **Location:** `aquilia/models/fields_module.py` `ForeignKey.sql_type()` (~line 2696): falls back to `"INTEGER"` when `_resolve_pk_field()` cannot resolve the target. `aquilia/cli/commands/model_cmds.py` `cmd_migrate()` (~line 365): unlike `cmd_makemigrations`/`cmd_diff`, it never imports the workspace models, so `ModelRegistry` is empty at apply time. Generated migration files render `fields.ForeignKey("User")` (string target).
- **How discovered:** applied the generated initial migration to a scratch Postgres: `foreign key constraint "auth_events_user_id_fkey" cannot be implemented … Key columns "user_id" and "id" are of incompatible types: integer and uuid`. The DDL *did* include the `REFERENCES users(id)` clause (from `ColumnState.reference`), with the column typed `INTEGER`.
- **Actual behavior:** migrations generated by the framework's own `makemigrations` cannot be applied by the framework's own `migrate` when FK targets have UUID primary keys.
- **Expected behavior:** the migration file is self-describing (per `CreateModel`'s own docstring: "fully describes the table it creates, with no reference to the model classes") — the FK column type must travel in the file.
- **Impact on AniWave:** all 6 tables have `user_id uuid` FKs; the initial migration was un-applyable as generated.
- **Workaround used:** hand-edited the migration file: `fields.ForeignKey("User")` → `fields.UUIDField()` while keeping `column="user_id", reference=Reference(model="User", table="users")` — the DDL renderer takes the REFERENCES clause from `reference` and the type from the field class, so this is both correct and self-contained. Verified: migration applied cleanly on two scratch databases; structural diff vs the converted dev DB showed only index-direction and constraint-name differences.
- **Recommended fix:** codegen should emit the resolved column type for FK columns (e.g., `ColumnState.of("user", fields.UUIDField(), column="user_id", reference=Reference(...))`) — or the engine should pass target PK type through `Reference`. Add an apply-test for a UUID-PK schema.

### F-03 — `CompositePrimaryKey` is exported and documented but not wired into the model metaclass

- **Severity:** Major
- **Status:** confirmed + workaround (surrogate PKs)
- **Affected Aquilia component:** ORM — `aquilia/models/fields/composite.py`, `aquilia/models/metaclass.py`, `aquilia/models/options.py`
- **Location:** `composite.py` (~line 325) documents `class Meta: primary_key = CompositePrimaryKey(fields=[...])` and states "The metaclass reads this from Meta". `metaclass.py` (~lines 180–203) only checks `f.primary_key` on **fields** and auto-injects `id = BigAutoField()` when none exists; `Options` never reads `Meta.primary_key` (no reference in `options.py`). No framework test references `CompositePrimaryKey` (grep across `tests/` = zero hits; only the docs-site React files and package exports mention it).
- **How discovered:** declared `Meta.primary_key = CompositePrimaryKey(...)` on Watchlist/WatchProgress/NotificationRead; runtime inspection showed `_meta.primary_key` missing, and the generated migration added a spurious `id = BigAutoField()` column to each.
- **Actual behavior:** documented API is a no-op; composite-PK tables silently gain a surrogate bigint `id`.
- **Expected behavior:** composite primary keys per the docstring, or the API removed.
- **Impact on AniWave:** three tables carry surrogate `id` PKs plus `UNIQUE` constraints on the original key columns. Integrity semantics are identical (uniqueness enforced; ids never appear in API responses), but the schema deviates from the Node/drizzle end-state and the dev DB needed in-place conversion (drop composite PK, add `id bigserial`, add unique constraints).
- **Workaround used:** surrogate `BigAutoField(primary_key=True)` + `UniqueConstraint(fields=[...])` per table; documented deviation.
- **Recommended fix:** wire `Meta.primary_key` into `Options`/metaclass (skip auto-PK injection, emit table-level `PRIMARY KEY (...)`), or delete/flag the dead API. The migration `backends/__init__.py` already renders `PrimaryKeyConstraintState`, suggesting partial intent.

### F-04 — `aq` CLI silently rewrites hand-written workspace module configuration; the preservation regex requires a single-line block opening

- **Severity:** Major
- **Status:** confirmed + workaround (formatting convention)
- **Affected Aquilia component:** CLI — `aquilia/cli/generators/workspace.py`
- **Location:** `_extract_existing_module_blocks()` (~line 104): `re.match(r"\.module\(Module\(\s*[\"\']([^\"\']+)[\"\']", stripped)` — requires `.module(Module(` on **one line**. `update_workspace_config()` strips all `.module()` blocks and re-inserts them (or regenerated defaults) before the integrations section.
- **How discovered:** twice. (1) `aq add module … --route-prefix "/api"` wrote `.route_prefix("/core")` etc. — the `--route-prefix` value never reached `workspace.py` (see F-05). (2) After I hand-wrote multi-line blocks — `.module(\n    Module("core", …)` — the next `aq run` printed "✅ Updated workspace.py with 6 module configurations" and replaced them with default `/<name>` prefixes and **no** `depends_on`, breaking cross-module DI.
- **Actual behavior:** hand-authored module config is silently regenerated (route prefixes reset, dependencies dropped) when the block doesn't match a formatting regex the user has no way to know about.
- **Expected behavior:** `aq` either preserves user configuration regardless of formatting, or refuses to run with a parse warning instead of silently discarding it.
- **Impact on AniWave:** one full debugging cycle (routes 404ing at `/auth` instead of `/api/auth`) plus a defensive comment in `workspace.py`; also the recurring anxiety that any `aq` command may rewrite the file.
- **Workaround used:** keep `.module(Module(` on a single line (documented in a workspace comment); re-verified prefixes survive subsequent `aq run` invocations.
- **Recommended fix:** make block preservation parsing-based (AST) or marker-based instead of regex-on-adjacent-tokens; never delete unrecognized `.module()` content — emit it unchanged.

### F-06 — Route decorator `status_code=` is not applied to handler results (silently wrong HTTP status)

- **Severity:** Major
- **Status:** confirmed for plain-dict returns + workaround
- **Affected Aquilia component:** controller engine — route decorators vs `_to_response`
- **Location:** `aquilia/controller/engine.py` `_to_response()` (~line 1828) converts `dict/list` → `Response.json(result)` with no consultation of route metadata `status_code`; the `@POST(..., status_code=…)` parameter exists on every verb decorator (and the reference example uses it).
- **How discovered:** `POST /api/auth/register` decorated with `status_code=201` returned **200** (verified live with curl during the auth flow bring-up). Node returned 201; the client distinguishes.
- **Actual behavior (verified):** dict-returning handler + `status_code=201` in the decorator → 200 response. (Whether any other return path honors it was not pursued once the workaround was in place — scope of the confirmed defect is plain dict/list returns.)
- **Expected behavior:** documented decorator parameter takes effect.
- **Impact on AniWave:** every non-200 success (201 register/guest/watchlist-add/comments, plus explicit 204s) had to return `Response.json(..., status=…)` / `Response(status=204)` by hand; the decorator parameter is dead weight we now distrust.
- **Workaround used:** explicit `Response` construction in all non-200 handlers.
- **Recommended fix:** apply route `status_code` in `_to_response` (or remove the parameter). Add an example-app test asserting a 201.

### F-07 — `NativeTransport` collapses duplicate response headers (multi `Set-Cookie` loss)

- **Severity:** Major
- **Status:** confirmed (source) + workaround verified live
- **Affected Aquilia component:** HTTP client — `aquilia/http/_transport.py`
- **Location:** `_read_response_head()` header loop (~lines 516–530): `headers[name.strip()] = value.strip()` — dict assignment, last occurrence wins. `HTTPClientResponse.get_headers()` (~response.py line 265) can therefore never return multiple values for the same name.
- **How discovered:** the provider scrapers depend on multi `Set-Cookie` responses (anizone Livewire sets XSRF + session cookies in one response; animeonsen's `ao.session`; mkissa's rotating cookie jar). Reading the transport source while porting them showed the collapse; a bare-dict fallback in mkissa's `store_cookies` confirmed the shape.
- **Actual behavior:** only the last `Set-Cookie` line survives parsing.
- **Expected behavior:** multi-value headers are preserved (RFC 9110 §5.2 field-line combining, or a raw list kept for `Set-Cookie` which is the known exception to combining).
- **Impact on AniWave:** Livewire-CSRF and session-boot flows would silently break (cookie missing → 403 loops).
- **Workaround used:** `provider/providers/_http.py:_MultiHeaderTransport` — a `NativeHTTPClient`-compatible subclass overriding `_read_response_head` to **join** duplicates with `", "` (matching RFC combining), plus `split_set_cookie()` / `set_cookie_values()` helpers that split on `,(?=[^;,]+?=)` so date commas inside `expires=` don't split. All provider flows load and the cookie-based scrapers work through this transport. The injection point (`AsyncHTTPClient(transport=…)`) is a genuine framework strength that made this possible.
- **Recommended fix:** keep a raw `(name, value)` list on the parsed response and expose `get_list(name)`; join-on-duplicate at minimum for `set-cookie`.

### F-08 — Response bodies are lazy while connections are recycled; reading after client close races (SSL errors / truncated bodies)

- **Severity:** Major
- **Status:** confirmed (runtime) + workaround (buffer in-context)
- **Affected Aquilia component:** HTTP client — `AsyncHTTPClient`/`HTTPSession`/`NativeTransport` lifecycle
- **Location:** `NativeTransport.send()` (~lines 643–733) returns a response wrapping a lazy `body_stream()` and its `finally` **returns the connection to the pool**; client/session `close()` → `pool.close_all()` closes pooled connections. `ConnectionInfo.close()` swallows its own exceptions, but the in-flight read of a closed connection surfaces elsewhere.
- **How discovered:** stream probing failed with `ssl.SSLError: [SSL: APPLICATION_DATA_AFTER_CLOSE_NOTIFY] application data after close notify` for a URL that verifiably worked. Minimal reproduction: `res = await client.get(url)` inside `async with AsyncHTTPClient(...) as client:` then `await res.text()` **after** the block → SSL error; reading (`await res.read()`) *inside* the block → `GOT BODY: 2379153 status: 200`.
- **Actual behavior:** the natural usage pattern (`res = await client.get(...); ...; await res.text()`) is unsafe once the client context exits — the body stream reads from a connection the pool may have closed. The same error intermittently appeared inside the provider race engine (`kaa`) before the fix.
- **Expected behavior:** either bodies are eagerly buffered (they end up buffered anyway in `read()`), or the pool defers closing connections with unconsumed streams, or the response raises a clear "body not read before close" error instead of an SSL traceback.
- **Impact on AniWave:** every provider HTTP helper and the streaming proxy had to be audited and fixed to buffer bodies inside the client context; one full debug cycle on "network" probe failures that were actually lifecycle races.
- **Workaround used:** `await res.read()` inside every `async with` block before returning the response (`provider/providers/_http.py`, streaming probes, media proxy). Per-response memory is bounded by segment size.
- **Recommended fix:** document the lifecycle contract and/or make `send()` read the body eagerly when the response is not explicitly requested in streaming mode; make pool close await outstanding stream readers or detach their connections.

### F-09 — `update_or_create` / `get_or_create` are not concurrency-safe (no atomic upsert)

- **Severity:** Major
- **Status:** confirmed (test) + workaround
- **Affected Aquilia component:** ORM — `Manager.update_or_create` / `get_or_create`
- **Location:** `aquilia/models/manager.py` (~line 436/492) — check-then-insert without `ON CONFLICT`.
- **How discovered:** the AniWave stress suite (10 concurrent `POST /api/progress` on the same row) failed with `duplicate key value violates unique constraint "watch_progress_user_id_anilist_id_episode_key"` → `QueryFault` → HTTP 404. Node used a single-statement `INSERT … ON CONFLICT DO UPDATE`.
- **Actual behavior:** concurrent creators both pass the existence check; the loser's insert raises a unique-violation fault.
- **Expected behavior:** an atomic upsert primitive, or documented non-guarantee with a retry recipe.
- **Impact on AniWave:** progress saves, watchlist adds, and notification-read marks were all racy under the concurrent usage the client actually performs.
- **Workaround used:** `_upsert_retry()` in `modules/library/services.py` — retry on unique-violation (loser re-runs and takes the update path). Stress tests now pass (concurrent watchlist add → single row; concurrent refresh → exactly one rotation winner).
- **Recommended fix:** add `ON CONFLICT DO UPDATE/NOTHING` support on Postgres (the builder already targets PG), or make the manager retry unique violations internally.

### F-12 — Framework auth HTTP middleware auto-activates from the config section and enforces its own keyring against all Bearer tokens

- **Severity:** Minor (footgun)
- **Status:** confirmed (runtime) + workaround
- **Affected Aquilia component:** auth integration middleware
- **Location:** `aquilia/server.py` (~lines 381–420): `use_auth = auth_config.get("enabled", False)` — defining `class auth(AquilaConfig.Auth)` (I only set `secret_key` and `password_hasher`) leaves `enabled` at its truthy default, mounting `AquilAuthMiddleware` with default `TokenBackend`/`SessionBackend` and the framework's own signing key.
- **How discovered:** with a valid app-issued JWT (HS256, `JWT_SECRET`, `kid="aniwave-active"`), `GET /api/auth/me` returned `403 {"code":"AUTH_002","message":"Invalid token"}` — the framework middleware validated the Bearer token against **its** keyring (`AQ_SECRET_KEY`) before my per-route decorator ran.
- **Actual behavior:** an application that manages its own tokens is silently intercepted by framework auth with a different key store; public routes that carry an (app-invalid) token also get rejected.
- **Expected behavior:** opt-in HTTP auth enforcement, or at minimum explicit `backends`/`enforce` configuration; an app-level token scheme should not collide by default.
- **Impact on AniWave:** 403s on valid tokens until diagnosed; also the reason the app's own `@require_auth` (stateless, per-route, Node-guard semantics) had to be built.
- **Workaround used:** `enabled = False` in `BaseEnv.auth`; app auth via `app/auth.py` (`TokenManager` with HS256 KeyRing over `JWT_SECRET`, `sid` claim, in-memory token store = stateless verify exactly like the Node guard).
- **Recommended fix:** default `enabled=False`; document the interplay between the framework auth pipeline and app-managed bearer schemes.

- **Status:** confirmed (runtime) + workaround

### F-18 — App boots with pooled DB/Redis require session-scoped pytest loops; no framework guidance or fixture support

## 3. Aquilia vs NestJS (practical, migration-relevant)

**Equivalent capabilities (verified in use):** modular controllers with prefixes/tags; constructor DI with module scoping; request-body DTO validation with per-field errors; guards → hand-rolled decorators (same contract); interceptors → middleware (merged ours with error rendering); OpenAPI (Specula vs Swagger — less granular, no per-route `@ApiQuery`-level metadata control); env-layered config.

**Missing NestJS functionality encountered:** per-route `status_code` actually applying (F-06); `ParseIntPipe`-style param validation with 400 semantics (F-26); a throttler matching a custom fixed-window contract (Aquilia's `Throttle`/`RateLimitIntegration` exist but produce a different error body/semantics than the Node contract — hand-rolled Redis limiter instead); exception-filter registration hook (F-20); DI into HTTP middleware.

**Weaker abstractions:** the migration system vs Drizzle's (F-01/F-02/F-03/F-14); the HTTP client's response lifecycle vs undici/fetch (F-08); header fidelity (F-07).

**Stronger / cleaner:** single-file workspace with Python env classes (vs Nest's scattered module wiring); explicit manifests; DI without decorator ceremony; Contracts as `Annotated` types with wards (nicer than class-validator decorators); a real task subsystem (Nest has none built in); zero-dependency native HTTP with a public transport extension point; `aq validate`/`inspect` (Nest CLI has no equivalent static app check).

**Migration friction (ranked):** 1) migrations (two critical defects), 2) HTTP client lifecycle/header fixes across ~10 provider files + proxy, 3) test-infrastructure loop/query quirks, 4) auth middleware collision, 5) workspace rewriter. Everything else ported 1:1 or better.

**Where NestJS is more mature:** validation ecosystem (zod/class-validator), ORM/migration tooling, docs/community, per-route pipe/status composability, testing utilities (supertest semantics are boring in a good way).

## 5. Positive Findings (verified during the migration)

- **DI architecture**: container-per-module + `depends_on` links + token fallthrough to the owning container made a clean service-only `providers` module and painless cross-module injection (`ProviderService` → catalog/streaming). The framework's own pattern of sharing one cache service across containers (ValueProvider registration) is a sensible precedent we mirrored for metrics.
- **`transport=` extension point on `AsyncHTTPClient`**: the single hook that made F-07 fixable without forking — subclass, override one method, inject. Public, typed, documented.
- **Contracts**: `Annotated[str, Field(...)]` + nested contracts + `@ward` cross-field rules + automatic PATCH-partial mode mapped the zod DTOs almost 1:1; `bind_contract_to_request` merging body+query+path and the engine's contract-typed parameter binding worked on the first try.
- **ORM query API**: Django-style lookups, `.order()`, `F()` expressions in `update()` (comment likes), `update_or_create`, `exists`, `limit/offset` — the service-layer port from Drizzle was mechanical and fast.
- **CacheService**: fail-soft semantics + per-container auto-registration + TTL/namespace handling matched the Node fail-open design almost exactly; `get_or_set` stampede protection exists (we kept Node's single-flight semantics instead, deliberately).
- **`aq validate`**: caught a real manifest syntax error I introduced (duplicate kwarg) with a pointing error message; 9 checks, fast.
- **`aq inspect routes` / module scaffolding**: accurate route inventory (46) and useful generated structure.
- **Task system**: `@task` + `TaskManager` gave the fire-and-forget warm-up real lifecycle, timeout, and worker semantics — strictly better than Node's `setTimeout`.
- **Testing core**: in-process `TestClient` (no sockets), `set_bearer_token`, `raise_server_exceptions=False`, and the `aquilia.testing` pytest fixtures — once loop-scoped, the 108-test suite runs in ~2.3s.
- **Runtime phases**: `AquiliaRuntime.from_workspace(...)` → `configure/discover/bootstrap` + explicit `startup()/shutdown()` made a clean test boot; `auto_migrate=True` applied pending migrations to a fresh DB correctly (after the file was fixed).
- **`Env`/`Secret` primitives**: dotenv autoload + read-time resolution + `required=True` gave Node's fail-fast env contract with ~40 lines of app code.
- **Response API**: `Response(content, status, headers)` and `Response.json` covered every proxy/playlist/segment case; header mutation post-construction worked.
- **PasswordHasher / TokenManager**: argon2id with PHC auto-detection and an HS256 KeyRing with `sid` claims — exactly the primitives the auth service needed, stateless verification compatible.

## 6. Final Assessment

### Executive Summary
The AniWave backend was fully migrated to native Aquilia and verified (46 routes, 108/108 tests, `aq validate` 9/9, live boot with real dependencies and live provider traffic, live rate-limit enforcement with byte-exact error contracts). The migration succeeded because Aquilia's application-level primitives (DI, Contracts, ORM queries, cache, tasks, CLI, testing core) are genuinely good — and despite two critical defects in the migration system and several major correctness footguns in the HTTP client and ORM, all of which required workarounds that are now load-bearing parts of `backend/`.

### Critical Findings
- **F-01** `ArrayField` is unusable in migrations (silent serialization loss).
- **F-02** Generated FK migrations type UUID-keyed columns as INTEGER; apply fails.

### Major Findings
- **F-03** `CompositePrimaryKey` documented but unwired.
- **F-04** CLI silently rewrites hand-written workspace module config (also F-05 `--route-prefix` ignored).
- **F-06** Route `status_code=` not applied to dict returns.
- **F-07** Duplicate response headers collapse (multi `Set-Cookie` loss).
- **F-08** Lazy response bodies race connection recycling (SSL errors/truncation).
- **F-09** `update_or_create`/`get_or_create` not concurrency-safe.
- **F-10** Bare `EmailFacet` class silently disables validation.
- **F-11** Deprecated `depends_on` is load-bearing; the recommended replacement breaks DI.

### Minor Findings
F-13 (dry-run lie), F-14 (diff false drift), F-15 (late task binding), F-16 (SealFault surface), F-17 (TestClient query/accessors), F-18 (test loop scoping), F-19 (deprecated calls/naming), F-20 (no error-envelope hook), F-21 (docs drift), F-25 (FK attribute asymmetry), F-26 (int-converter semantics, suspected), F-27 (cache key layout).

### Missing Features (demonstrated by the migration)
Atomic upsert (`ON CONFLICT`); composite primary keys; array columns in migrations; configurable error rendering; per-route status application; DI into middleware; param-pipe validation with custom failure statuses; a documented app fixture for pooled test boots.

### Known Broken Areas
The migration toolchain end-to-end for non-trivial schemas (makemigrations → migrate) — both critical defects live there, plus misleading dry-run/diff output.

### Workarounds Introduced
17 entries — see §4. Items 1–6 and 8, 11–15 are genuine framework gaps that should be fixed upstream; the rest are app-contract fidelity.

### Aquilia vs Node.js Summary
Application runtime: equal or better (DI, tasks, config, cache). Data layer tooling: clearly worse (migrations). HTTP client: worse (lifecycle, headers). Testing: comparable once configured. DX: promising CLI undermined by the workspace rewriter and output lies.

### Aquilia vs NestJS Summary
Cleaner module/DI/contract design and a better task story; NestJS remains far ahead on validation ergonomics, ORM/migration maturity, per-route composability, and documentation accuracy.

### Recommended Aquilia Improvements (priority order)
1. Migration round-trip tests (model → snapshot → migration → apply → introspect) for UUID FKs, arrays, composite PKs — would have caught F-01/F-02/F-03 before release.
2. HTTP client: preserve multi-value headers; define (or fix) the body-read lifecycle.
3. Atomic upserts on Postgres.
4. Stop rewriting unrecognized workspace content; honor `--route-prefix`.
5. Apply (or remove) route `status_code`; error on bare facet classes; fix the SealFault surface.
6. Reconcile `depends_on`/`imports` and the deprecation guidance.
7. Regenerate GUIDE.md; document the testing loop-scope pattern; quiet boot noise (admin banner, signing warning provenance, Specula count).

### Migration Risks
- The workarounds (transport subclass, hand-edited migration, retry wrapper, custom middleware/guards) are now part of the app — upstream fixes may require deliberate reconciliation.
- The hand-edited initial migration diverges from what `makemigrations` would regenerate (checksum implications for applied-migration verification).
- Future schema changes involving arrays or composite keys will re-hit F-01/F-03 until fixed upstream.
- The `backend/` tree is uncommitted; the converted dev database is the only copy of the pre-existing dev data (a `pg_dump` snapshot was taken at `/tmp/aniwave_dev_backup.sql` during conversion).

### Overall Assessment
Aquilia carried the application architecture well — the port of services, controllers, contracts, and DI was faster and cleaner than the equivalent NestJS code in places. The price was paid almost entirely in the framework's data-layer tooling and HTTP-client details, where the migration had to debug and patch around the framework rather than with it. The result is a working, fully verified native Aquilia backend whose compatibility layer doubles as a precise bug list for the framework's next iteration.

# 7. Verification & Fix Report (2026-09-14, framework audit response)

Every finding above was independently re-reproduced against the Aquilia
framework source, root-caused, fixed in the framework, and covered by
permanent regression tests. The original observations in §1–§6 are preserved
verbatim above; this section records what verification found and what
changed. Status vocabulary: **CONFIRMED + FIXED** · **CONFIRMED + MITIGATED**
· **CONFIRMED — BY DESIGN** (not a defect) · **PARTIALLY CONFIRMED**.

Verification environment: Python 3.13.14, framework checkout at the repo
root, live PostgreSQL 16 (Docker) for F-02/F-09/F-14/F-03, live loopback
HTTP server for F-07/F-08, live Redis semantics reviewed for F-19.

## F-01 — ArrayField serialization — CONFIRMED + FIXED

- **Reproduction:** generated a migration for a model with
  `ArrayField(TextField(), size=10)`; the file contained a bare
  `fields.ArrayField()` and failed to import in a clean process with
  `ArrayField.__init__() missing 1 required positional argument:
  'base_field'` — the audit's exact error.
- **Root cause:** `ArrayField` never overrode `Field.deconstruct()`, whose
  base implementation serializes only
  `type/null/unique/primary_key/db_index` (+ conditional `db_column`,
  non-callable `default`).
- **Fix:** `ArrayField.deconstruct()` serializes `base_field` as a nested
  deconstruct dict (the same form `GeneratedField.output_field` uses) and
  `size` when set; `ColumnState.rebuild_field()` rebuilds nested
  `base_field` into a live field; the codegen renders
  `fields.ArrayField(base_field=fields.TextField(), size=10)`.
- **Files:** `aquilia/models/fields_module.py`,
  `aquilia/models/migration/schema.py`, `aquilia/models/migration/codegen.py`.
- **Tests:** `tests/test_migration_audit_regressions.py` (deconstruct
  content, file rendering, clean-process load, `TEXT[]` on postgres /
  `TEXT` on sqlite).
- **Verification:** `pytest tests/test_migration_audit_regressions.py`;
  `AQUILIA_TEST_POSTGRES_URL=... pytest` for the live-postgres variant.

## F-02 — UUID FK migrations typed INTEGER — CONFIRMED + FIXED

- **Reproduction:** generated a migration for a UUID-keyed model + FK
  child; loaded the file in a subprocess with an empty model registry (the
  exact `aq db migrate` condition) and compiled it for PostgreSQL: the FK
  rendered `"account_id" INTEGER NOT NULL REFERENCES "repro_accounts"
  ("id")` — un-appliable DDL, as reported.
- **Root cause:** the FK column type was derived at DDL-render time through

## F-03 — CompositePrimaryKey unwired — CONFIRMED + FIXED

- **Reproduction:** declared `Meta.primary_key =

## F-04 — CLI destroys multi-line workspace blocks — CONFIRMED + FIXED

## F-08 — Lazy bodies race connection recycling — CONFIRMED + FIXED

- **Reproduction (live):** `res = await client.get(...)` inside
  `async with AsyncHTTPClient()`, `await res.text()` after the block —
  previously SSL/truncation errors; now returns the body.
- **Root cause:** `send()`'s `finally` returned the connection to the pool
  while the response's body stream still owned the reader; pool
  `close_all()` then closed it under in-flight reads, and the pool could
  hand a dirty connection to the next request.
- **Fix (ownership model):** a created response takes ownership of the
  connection; its body-stream `finally` is the single release point
  (pool if keep-alive and alive, else close). `send()` releases only on
  the error paths. `ConnectionPool.close_all()` now sets a closed flag and
  `put_connection()` closes instead of resurrecting into a dead pool.
- **Files:** `aquilia/http/_transport.py`.
- **Tests:** `tests/test_http_client_audit_regressions.py` (read-after-close,
  connection reuse, unread-response non-poisoning, 8 concurrent requests,
  close-without-read).

## F-09 — Non-atomic get_or_create/update_or_create — CONFIRMED + FIXED

- **Reproduction:** the audit's exact scenario re-run against live
  PostgreSQL: concurrent same-key `update_or_create` previously produced
  unique-violation faults; stress now shows 10/50/100 concurrent callers →
  exactly 1 row, exactly 1 creator, 0 exceptions; 100 distinct keys → 100
  rows.
- **Root causes (three, layered):**
  1. `get_or_create`/`update_or_create` were plain
     SELECT-then-INSERT/UPDATE;
  2. **latent:** `find_or_create`'s created-detection used
     `cursor.lastrowid`, which goes stale on a reused connection (a
     conflicted upsert reported itself as created);
  3. **latent:** the PostgreSQL adapter hardcoded `rowcount=1` for every
     INSERT, so conflicted `ON CONFLICT DO NOTHING` inserts reported
     `rowcount=1` on PostgreSQL.
- **Fix:** both methods delegate to the atomic `INSERT ... ON CONFLICT DO
  NOTHING` path when the lookup fields are covered by a unique constraint
  (update_or_create then applies defaults via a lookup-filtered UPDATE);
  lookups without a unique constraint keep the legacy path behind a
  RuntimeWarning (atomicity is impossible without a conflict target).
  `find_or_create` keys on `rowcount`. The postgres adapter reports
  `rowcount = 0` when the RETURNING row is absent, and falls back to a
  plain execute when the auto-appended `RETURNING "id"` hits a table
  without an `id` column (composite-PK tables).
- **Files:** `aquilia/models/base.py`, `aquilia/db/backends/postgres.py`.
- **Tests:** `tests/test_orm_concurrency_warnings.py` (rewritten from
  "must warn" to the new contract: silent atomicity for unique lookups,
  warning only for non-unique, 10-way concurrent same-key, composite
  unique); mock-cursor fixtures in `tests/test_model_find_or_create.py`
  corrected to model real rowcount semantics.
- **Verification:** stress script against PostgreSQL at 10/50/100
  concurrency plus 100 distinct keys — all invariants held.

## F-14 — db diff false drift — CONFIRMED + FIXED

- **Reproduction:** migrated a schema to sqlite, diffed the introspected

## Edge case observed during stress verification (documented, not fixed)

Two `make_migrations` invocations within the same wall-clock second, from
**different migrations directories**, against a **shared database** produce
identical revisions (`YYYYMMDD_HHMMSS` has second granularity, and
`_next_revision` only checks collisions against the local graph). The
second migration is then silently treated as already applied and skipped,
leaving its tables missing. This is outside the designed model (one
migrations directory per project; the tracking table reflects that
project) and was hit only by this audit's stress harness, which uses a
fresh temp directory per run against one scratch database. Recommended
hardening for a future release: have `migrate()` compare checksums for
tracked revisions and raise a clear fault on a same-revision/different-
checksum collision (clock collision), while keeping `verify_checksums()`
as the drift reporter for the legitimate edit-after-apply case.

# 8. Post-audit session: admin subsystem defects (2026-09-14)

Two further defects were reported from production use of the admin
dashboard immediately after the audit work above. Both were reproduced
end-to-end before fixing; regression tests live in
`tests/test_admin_session_middleware.py`. Released in v1.4.1.

## Admin security DI provider registration — CONFIRMED (1.4.0) + FIXED

`LOG WARNING admin.security — Failed to register admin security DI
providers: ValueProvider.__init__() missing 1 required positional
argument: 'token'`. Root cause (v1.4.0): registration sites constructed
`ValueProvider(value)` without the required `token` and passed
`container.register(Token, Provider)` — inverting
`Container.register(provider, tag=None)`; `di_providers.py` additionally
referenced undefined `Scope` constants. Fixed in `aquilia/admin/security.py`
and `aquilia/admin/di_providers.py`; verified by registering into a real
container and resolving all six security providers plus
`AdminSite`/`AdminAuditLog`; a repository-wide AST sweep confirms no
malformed provider registrations remain.

## Admin login redirect loop — CONFIRMED + FIXED

**Symptom:** valid superuser credentials; `POST /admin/login` → `302
/admin/` with **no `Set-Cookie`**; `GET /admin/` → `302 /admin/login` —
an infinite, silent loop that looks like the page "just refreshed".

**Root cause:** in `AquiliaServer._setup_middleware`, the
`SessionMiddleware` mount and the `SessionEngine` DI registration were
nested inside `if use_auth:`. With sessions enabled and framework auth
disabled (apps that manage their own Bearer tokens — the shape this audit
itself recommends in F-12), the engine was created but never mounted or
registered: `ctx.session` stayed `None`, the login handler's identity
write went nowhere, and no middleware serialized a session cookie.

**Fix:** both are gated on the session engine existing
(`aquilia/server.py`); `AquilAuthMiddleware` still owns sessions when auth
initializes. A latent `UnboundLocalError` (function-local `ValueProvider`
import shadowing the module-level one, crashing the session-DI block when
auth was disabled) was removed.

**Verification:** superuser login issues the `aquilia_session` cookie and
`GET /admin/` renders 200; without a cookie the guard still redirects to
login; the auth-enabled path mounts `AquilAuthMiddleware` with no duplicate
session middleware; `SessionEngine` resolves from every DI container.
